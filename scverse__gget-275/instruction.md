# Issue

**Title:** fix(info): look up exon/translation IDs without Ensembl 'expand'

## Description

### Problem
`gget info` looks up every ID with `expand=True` and relied on Ensembl returning `null` for exon and translation IDs, which it then retried without expand. Ensembl now **rejects** `expand` for those IDs instead, so the whole call fails before the fallback runs. This is why `test_info_exon` fails on main.

Checked against the live Ensembl REST API (release 116):
- `GET lookup/id/ENSTGUEE00000179311` → 200 (exon is current, chr 1:107,526,792–107,526,965)
- `GET lookup/id/ENSTGUEE00000179311?expand=1` → **400**
- the batch `POST lookup/id` with `expand` returned **500** in CI (Oct 1 run)

### Change
- Ensembl exon/translation IDs (`ENS…E`/`ENS…P` + 11 digits) skip the expanded lookup and go straight to the existing no-expand pass
- If an expanded batch still fails, each ID is retried on its own, so one bad ID doesn't drop `expand` (transcripts/exons) for the others
- Network-free tests for ID detection, the per-ID fallback, and the query sent for an exon ID

### Not covered
- `test_info_gene` (`EnsMUSG00000000001`) also got a 500 on Oct 1, but a single `GET … ?expand=1` works today (Gnai3, 10 transcripts), so that looks transient. It's likely to keep failing on the missing NCBI fields, which is a separate issue.
- I couldn't send the batch POST from my environment, so CI is the first live run of the changed path.
